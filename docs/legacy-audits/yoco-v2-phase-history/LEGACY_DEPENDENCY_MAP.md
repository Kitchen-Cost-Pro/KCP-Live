# Legacy Yoco Dependency Map

This map records the active legacy integration, originally created in Phase 1-3 and revalidated for `phase-v2-12-yoco-legacy-shutdown`.

## 1. Webhook entrypoint and call chain

```text
POST /webhooks/yoco/:workspaceId
  cloudflare-v2/src/index.ts
    handle()
    -> forwardToWorkspaceDO(..., resource = "yoco-webhook")

  cloudflare-v2/src/workspace-do.ts
    WorkspaceDO.fetch()
    -> dispatchYocoV2Route() for isolated V2 admin/queue routes only
    -> dispatchWorkspaceRoute()

  cloudflare-v2/src/legacy/routes.ts
    dispatchWorkspaceRoute(resource = "yoco-webhook")
    -> postYocoWebhook()
      -> parse exact request body
      -> hashPayload()
      -> yocoWebhookEventFields()
      -> yocoWebhookEventDisposition()
      -> getYocoConnection()
      -> activeYocoWebhookSecrets()
      -> verifyYocoWebhook()
      -> captureVerifiedYocoV2EventSafely() after successful verification
      -> legacy yoco_webhook_events insert and processing claim
      -> loadYocoOrderForWebhook()
      -> processYocoOrder() and/or processYocoOrderReturns()
      -> update legacy webhook status and integration logs
```

V2 capture is a fan-out after the existing signature trust boundary. The legacy claim and processor remain in place.

## 2. Signature verification

Primary implementation:

```text
cloudflare-v2/src/legacy/yoco-webhooks.ts
  verifyYocoWebhook(rawBody, headers, webhookSecrets)
```

Secrets are loaded from the tenant `yoco_connections` record through `getYocoConnection()` and `activeYocoWebhookSecrets()`.

Invalid signatures are recorded through the existing rejection and integration log paths and never enter V2 capture or processing.

## 5. Sale processing and write paths

Main processor:

```text
cloudflare-v2/src/legacy/yoco-sales.ts
  processYocoOrder()
```

Supporting logic includes product mapping, recipe expansion, modifier mapping, location resolution, order readiness, and ingredient expansion through functions such as:

```text
  yocoOrderReadyForStock()
  expandProductIngredients()
```

Legacy sale writes include:

- `yoco_orders`
- `yoco_order_lines`
- `stock_movements`
- `stock_balances`
- processed signature and integration diagnostic state

The stock ledger rows generated by the legacy processor remain the live sale stock path.

## 6. Refund processing and write paths

Main refund processors:

```text
cloudflare-v2/src/legacy/yoco-sales.ts
  getOrderReturns()
  resolveRefundLineItems()
  resolveRefundReturnBehavior()
  processYocoOrderReturns()
  processYocoOrder() in refund processing modes
```

Refund processing resolves the original order and line context before writing legacy return movements and updating the legacy sale/refund records. The active refund write paths include:

- `stock_movements`
- `stock_balances`
- `yoco_orders`
- `yoco_order_lines`
- `yoco_webhook_events`
- integration diagnostics

V2 has no import of these legacy processors and no write statement for these business tables.

## 10. Integration credentials and secrets

Legacy credentials are stored in or derived from:

- `yoco_connections.api_key_encrypted`
- `yoco_connections.webhook_secret`
- previous webhook secret fields used during safe rotation
- `YOCO_KEY_ENCRYPTION_SECRET`
- `YOCO_WEBHOOK_BASE_URL`

Credentials are decrypted only in the legacy service/client path. V2 stores no API key and puts no credential in queue payloads or diagnostic headers.

## 12. Ownership boundary

Legacy owns all four effects in this release:

```text
SALE_REPORTING   -> LEGACY
SALE_STOCK       -> LEGACY
REFUND_REPORTING -> LEGACY
REFUND_STOCK     -> LEGACY
```
